# /scout: the hosted Flow route

The router (`skills/scout/SKILL.md` and `prompts/scout/router-build.md`) and `build.md` still govern targeting, confirmation, write order and dispositions. This route generates Flow XML with Salesforce's hosted metadata-experts server, through the official `salesforce-development` plugin's own proxy, pinned to the bound org. `sf-flow` stays the fallback. The orchestrator runs this route in write order. It is the one exception to `skills/scout/SKILL.md`'s MCP rule, because the helper binds the proxy to the bound org itself; that binding was verified for `salesforce-development` 2.3.0–2.5.0, and receipts record the version used.

Helper: `python3 [PLUGIN_ROOT_ABS]/scripts/scout_metadata_experts.py [COMMAND] --host [SCOUT_HOST] --selector [SELECTOR] --username [BOUND_USERNAME] --org-id [BOUND_ORG_ID]`. It prints one JSON object; act on `state`. It never deploys, never prints a token and never changes defaults.

## Inspection
Before proposing, for each Flow item:
1. Resolve `already_satisfied` first (`${CLAUDE_PLUGIN_ROOT}/prompts/building/phase2.md` §"Flow Rules" step 3). A satisfied Flow needs no hosted call and no activation.
2. Use the task's official inspection (`${CLAUDE_PLUGIN_ROOT}/prompts/building/official-skill-overrides.md` §"Readiness"). On `auto-deploy` or `deploy-gate`, follow its §"The official hooks" and use `sf-flow` until they're cleared. The hosted route also needs `flow-hosted` ready.
3. Run `status --probe`. `ready`: the hosted route. `activation-needed`: offer activation. `inactive`: activated but not live yet; `sf-flow`. `no-official-plugin`, `unavailable` or `unknown`: `sf-flow`, with the reason in the handover, and no activation offer.
4. Only for `activation-needed`, add a separate line to the bundled confirmation: "Activate metadata-experts in [ORG]: org-wide, beta, may be billed." Approving the Flow doesn't approve activation. When the task needs no other confirmation, still ask the activation line on its own. Without AskUserQuestion, ask in plain text and wait for an explicit answer to the activation line; no answer or an unclear one means no activation and `sf-flow`.

## Activation
On the SE's yes only, run `activate --confirmed`. It writes the Tooling API's `McpServerAccess` record, which Setup's Activate button creates but Salesforce doesn't document, then reads it back. `active` with `readiness: ready` continues on the hosted route. `active` with any other readiness is "activated, not ready yet", then `sf-flow`. `unverified` means the write may still land: record the output's `before`, `mutation` and `after` in the task record and run `status` before any retry. Record the activation outcome separately from the Flow's, with that evidence.

## Generation
Generate only after the Flow's dependencies are deployed and read back, because grounding reads the org. Run one hosted Flow at a time, at most three per task unless the SE approves more.
1. Before the first hosted call, tell the SE in one line: "Flows are generated by Salesforce's metadata-experts server, and Salesforce may bill hosted MCP usage."
2. Write the prompt file: the exact label, marked as must-keep, then object, trigger type, record trigger, entry conditions, whether a change into the criteria is required, the actions, Draft status and the API version.
3. Run `flow --prompt-file [P] --out-dir [TASK_DIR]/hosted/[ITEM] --candidate 1`. A candidate number is never reused.
4. On `complete`, write the spec JSON (`max_api_version`, `object`, `trigger_type`, `record_trigger_type`, `filters` with typed values, `filter_logic`, `requires_change`) and run `check --xml [XML] --spec [SPEC]`. The generator often renames the label; `check` reports it, and the handover names it. On `accepted`, copy the XML unchanged to `flows/[API_NAME].flow-meta.xml` in the writer project and validate it with a bound `--dry-run` deploy, which is the org's evidence that every referenced object and field exists. On `rejected`, or a dry-run failure the XML caused, sharpen the prompt with the named problems and generate candidate 2. A second failure or any other state: `sf-flow` authors a separate Flow with the approved API name.
5. Never edit hosted XML; its `processMetadataValues` (CanvasMode) are allowed. Transport failures and missing evidence never earn a new candidate.
6. Then follow `${CLAUDE_PLUGIN_ROOT}/prompts/building/phase2.md` §"Flow Rules" step 3's Draft deployment and exact version attribution, and step 4. Freeze obligations from the approved semantics: a positive one, and a negative one proven by a rolled-back runtime check (a FlowTest can't run a Flow whose entry conditions exclude the record), either "an edit that leaves the qualifying fields unchanged doesn't fire" (change-only) or "a save that doesn't meet the criteria doesn't fire" (every qualifying save). The two candidates cover pre- and post-deployment together; after that, repairs go to `sf-flow`, within the one shared repair budget.
7. In the handover, report the route, the activation outcome, the receipts' `client_rpc_calls` (client requests, not billable units) and any fallback reason. When any output carries `sidecars_left`, tell the SE the helper couldn't remove the official proxy's diagnostic files from Scout's cache.
