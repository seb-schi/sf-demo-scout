# Driving Salesforce's official skills

Scout routes Salesforce work to the skills of Salesforce's official Claude plugins, always by their qualified names, such as `salesforce-development:platform-apex-generate`. They come from Salesforce's own GitHub marketplace, never Anthropic's copy. This contract overrides only what it names. Every caller rule for scope, category permissions, retries, preservation and acceptance stays binding. A missing dependency is evidence to report, never authorization to install, upgrade, broaden work, substitute unrelated work or mark a check passed; the one exception is the missing-plugin repair below, which says when it asks first.

## Readiness
Before any inspection, worker dispatch, proposal or write in a build or repair, run `python3 -B "[PLUGIN_ROOT_ABS]/scripts/scout_official.py" inspect --host [SCOUT_HOST] --launch-dir "[the folder this session started in, else the verified workspace]"` once per task. It reports each capability's state on disk, the resolved plugin roots and the coexistence issues; its blocked items, install lines and coexistence notes join the bundled confirmation.
- `installed`: before a skill's first use in this session, confirm its qualified name is in your skill list. If it isn't, it needs a reload: ask the SE to run `/reload-plugins`, then resume. When a skill loads, pass the base directory it shows to `python3 "[PLUGIN_ROOT_ABS]/scripts/scout_official.py" verify --host [SCOUT_HOST] --plugin <plugin> --skill-dir "<base directory>" --launch-dir "<the same folder as the inspection>"`, once per plugin per task. Anything but `verified` stops that item, reporting the result's action.
- `installable` or `disabled`: use the missing-plugin repair.
- `setup-needed`, `unknown`, `conflict`, `missing` and `unsupported-host`: the items that need it are `BLOCKED`, with the reported action. Independent items proceed. A `conflict` whose `switched_on_in` names this folder's own settings file is the SE's to switch off there; Scout never changes project plugin selections.
- `notes` never block. `pinned`: say once that the SE's Salesforce plugins are fixed to that ref and `/scout-setup` can switch them to the latest. `personal_copies` with folders: say once that there are possible personal copies of Salesforce skills there, outside Scout's automatic updates, and that Scout uses the plugins' versions; a renamed skill isn't detected. `personal_copies: "unknown"`: say nothing.

**Industry knowledge.** When the request names or touches an industry or product cloud, such as Life Sciences or Net Zero, run `python3 -B [PLUGIN_ROOT_ABS]/scripts/industry_sources.py list` in this step. Then follow `${CLAUDE_PLUGIN_ROOT}/prompts/scout/industry-sources.md` before the proposal: it checks for a covering cartridge first, its knowledge informs the build, and these skills still make every change.

From then on, apply §"The official hooks" in this session, and copy it into every worker brief with the qualified names and resolved roots; workers don't re-check.

## Missing-plugin repair
When the plugins aren't set up at all (`setup-needed`, as right after an update from Scout 2.0), Scout repairs its own setup: say in one line, before inspection, "Scout builds with Salesforce's official plugins, which aren't installed yet, so I'm installing them now. It takes about a minute, and they keep themselves up to date." Then run the first bash block of `prompts/setup/official-plugins.md` with `--keep-se-choices`, with this session's launch folder and a 10-minute timeout, and surface its lines as that file does; then ask the SE to run `/reload-plugins`, and resume the same task once readiness passes. A failure leaves the build items blocked; read-only work goes on.

Otherwise this repairs one plugin that failed to install, was removed or was switched off. When a proposed item needs an `installable` or `disabled` plugin, the bundled confirmation names it in one line: "This needs Salesforce's <plugin> plugin, which Scout will install from Salesforce's GitHub marketplace." For `experience-lwc`, add: "It checks every HTML, CSS and JavaScript file Claude writes, in any project, not only Scout's." On the yes, run `python3 -B "[PLUGIN_ROOT_ABS]/scripts/setup-official-plugins.py" --host [SCOUT_HOST] --plugins <plugin>` with a 10-minute timeout and surface its lines as `prompts/setup/official-plugins.md` does. Record the task as waiting for the reload in the change log, ask the SE to run `/reload-plugins`, and resume that same task only after readiness and coexistence pass again. A decline or a failure leaves those items blocked; independent items proceed.

## Other official plugins
Salesforce's marketplace has more plugins than the five setup installs. `inspect` lists them under `optional`, each with the area it covers and its state. When a proposed item falls squarely in one of those areas and its plugin is `installable`, offer it in the bundled confirmation, in one line: "Salesforce has an official plugin for [area]: [plugin]. Want me to install it for this build? It stays installed and updates automatically." Offer each optional plugin the build squarely needs as its own line with its own yes, and never one it doesn't need, just in case: every installed plugin makes each Claude session a little heavier. On a yes, install and resume it as the missing-plugin repair does, then use its skills by qualified name under this contract. On a no or a failure, build the item the way Scout otherwise would; declining blocks nothing. An already `installed` optional plugin is used without an offer. Never offer `dx-org-lifecycle` or `salesforce-test-drive`: the map says why. A `dx-devops` skill's first `sf devops` command installs Salesforce's DevOps Center CLI plugin without asking: name that install in the same line.

## The official hooks
- **Skills first.** The official plugin denies raw `sf data query`, `sf project retrieve`, `sf apex run test` and `sf project generate manifest`, and a written `package.xml`, unless their owning skill loaded in this turn: `salesforce-development:platform-soql-query` (or `salesforce-development:platform-data-manage`), `salesforce-development:platform-metadata-retrieve`, `salesforce-development:platform-apex-test-run` and `salesforce-development:platform-manifest-generate`. Load the owning skill before the first such command in each turn and in each worker; after a "Skills-first enforcement" deny, load the skill it names and rerun the same command once. The hook matches those words anywhere in a command, so never put them inside another command's text, such as a heredoc; write the change log with the edit tools.
- **Dry runs.** Salesforce's deploy skill validates with `--dry-run` before a deploy. A dry run is a job too: give its ID its own `job:` line with `status:`, `launched:` and `settled:`, exactly as `commands/scout.md` records a deploy. It writes nothing, and its terminal status settles it.
- **Deploy gate.** Before every `sf project deploy` it checks the session's default org, whatever `--target-org` says. On `deploy-gate` with `no-default` or `default-unreachable`, ask the SE once, in plain words, before the first deploy: "Before every deploy, Salesforce's plugin double-checks your default org: the org Salesforce tools use when nobody names one. [No default is set right now. / Right now your default org, [default], can't be reached; its login may have expired.] So it would stop my deploy to [bound org], even though I always name the org I deploy to. Can I make [bound org] your default [for your project folder [folder] / on this computer]? That only changes which org is used when none is named, and you can change it back any time." Use "for your project folder" with the issue's `folder` when its `scope` is `project`, and "on this computer" when it's `global`. This is the one exception to `commands/scout.md`'s "Keep defaults … unchanged", and it needs an explicit yes. On the yes, run `sf config set target-org [bound username]` in the issue's `folder` (with `--global` instead when the scope is `global`), log it (why: Salesforce's deploy check; via: that command), and rerun the inspection to confirm `checks.deploy-gate: ok` before deploying. On a no, change nothing: the deploy items are `blocked`, because Salesforce's plugin will stop them. With scope `environment`, a setting in the SE's environment (`SF_TARGET_ORG`, `SFDX_TARGET_ORG` or `SFDX_DEFAULTUSERNAME`) decides the default, which Scout can't change: say so and report the deploy items blocked. With `query-failed`, the check itself failed: say so, change nothing, and let the first deploy show whether the gate allows it. In a team (`prompts/scout/team.md`), never offer the team's common org as the default: writes there go only through the captain's delivery.
- **Production gate.** When it denies a deploy as production, ask once per task: "The Salesforce plugin treats [org identity] as production. Do you approve applying [the approved changes] there?" Only an explicit yes counts. Then rerun each non-destructive deploy command within that approved scope with `CONFIRM_PROD=1` prefixed to that command only, never exported. A deploy outside that scope asks again. Destructive deploys stay blocked; they go to the SE's checklist.
- **Auto-deploy.** On `auto-deploy`, write no source; ask the SE to switch off `SFDX_AUTO_DEPLOY`, because the official plugin would deploy saved files to its own default org.
- **Recommender.** On `recommender`, expect at most one pause per session. When a "Plugin-catalog match" deny appears, relay its suggestion to the SE in one line and continue on their answer; never install from it without their yes.
- **Agentforce guardrails.** `agentforce-adlc` blocks DELETE or UPDATE without WHERE, `sf agent publish` without `--json`, and `.agent` files in a project deploy. Comply rather than work around them.

## Binding and confirmation
- Every command uses `--target-org [bound username]`, whatever a skill shows. A skill's `sf org login web --set-default` or `sf config set target-org` step is skipped, never run.
- Scout's bundled confirmation stands in for each skill's own confirmation gate, but satisfies only the approved target, action and delta. Preserve an incumbent description unless its replacement was approved. Delete, org-wide and billable approvals stay separate.

## Flow scope
Flow work inside or handed off from an official skill goes to Scout's Flow route (`prompts/scout/hosted-flow.md`, then `sf-demo-scout:sf-flow`), never an official skill's own hosted pipeline, which runs through the session's shared proxy and its default org. The maintained `sf-flow` skill owns its bundled handoffs and FlowTest schema and templates. Only execute an exact approved schema dependency through its named skill; a Flow-only phase or repair can't execute unrelated schema or agent work. An absent or unapproved dependency stays BLOCKED. Preserve Scout's exact required-test set, version, activation and rollback contract in Phase 2.

## Analyzer prerequisites
Run Code Analyzer through `salesforce-code-quality:dx-code-analyzer-run` (the `sf code-analyzer run` CLI), also where a skill or prompt says MCP `run_code_analyzer`, and only when its own prerequisite checks succeed. Do not delegate to an analyzer-configuration skill, do not install or upgrade tools, and do not disable required engines. If prerequisites fail or an engine doesn't start (PMD and CPD need Java 11 or later), preserve the exact failure and scan gap. A successful scan supports only the coverage it actually ran. If the analyzer is unavailable, state `scan not run/unverified` and keep required scan acceptance unresolved.

## Report tools
When the named API-context tools are unavailable, use the static `column-names.md` reference under the `report` capability's resolved `salesforce-development` root (`skills/platform-report-generate/references/column-names.md`) and the existing Phase 1 report fallback and read-back rules. Pass its absolute path to workers. Never fabricate tool calls or treat a static mapping as live validation. Unknown columns require supported evidence or documentation; otherwise they are BLOCKED before writing. Preserve exact filter values, filter logic, ReportType and folder identity, incumbent originals, and post-deploy read-back.

## Validation formulas
Correct official `ISCHANGE()` guidance to Salesforce `ISCHANGED(field)` before deployment. Preserve formula semantics, CDATA, error placement, and existing validation rules. Do not perform blind text replacement inside literal strings. This caller instruction is not an executable formula parser and does not prove live validation.

## FlexiPage scope
All new whole RecordPages remain manual/App Builder work; never run the official FlexiPage generator as a substitute for completing the requested page. A supported direct edit is limited to Phase 1's compatible field-section append path with a confirmed page, confirmed section and column, incumbent preservation, and read-back. Other component changes remain explicit manual/BLOCKED work under current scope.

## Email-to-Case scope
Keep Scout's base scope: `CaseSettings` and routing addresses. Under Scout this skill never creates or modifies Agentforce agents and never assigns channels, whatever handoff it suggests: Phase 3 owns separately approved email-agent entitlements, and channel assignment stays manual. The apply scripts run from the `email-to-case` capability's resolved `service-engagement` root; the email-agent probe, `check-agent-email-capability.sh`, needs the `email-agent-probe` capability and runs from the same root.

## Agentforce prerequisites and precedence
Scout's orchestration may use its named skills and MCP tools despite `agentforce-adlc:agentforce-generate`'s global no-dependencies statement. This is a Scout caller override, not a claim about upstream intent. Phase 3 owns metadata MCP operations, `sf agent` owns lifecycle operations, and `agentforce-adlc:agentforce-test` owns testing and schema guidance. Use an Agent Script compiler only if one is already available; never install its SDK or run npm setup for it. Otherwise validate against the target org and report "compiler not used".

Before a selected simulated programmatic authoring preview, capture a successful `sf --version` result and actual command readiness. Every selected help probe must exit 0 and expose all required flags: `sf agent preview start --help` must expose `--authoring-bundle`, `--simulate-actions`, and `--use-live-actions`; the selected send/end command help must expose send: `--utterance`, `--session-id`, and `--authoring-bundle`; end: `--session-id` and `--authoring-bundle`. The send/end commands do not take the action-mode flags. Start with `--authoring-bundle` and `--simulate-actions`. A published `--api-name` preview executes real actions and cannot substitute for this simulation. Salesforce CLI 2.130.9 release notes are dated context for the action-mode selection, but numeric version alone is not capability proof. Do not install or update anything. Do not silently use `--use-live-actions`, and never use a live-action fallback for failed simulation readiness.

A failed or unknown prerequisite leaves only this simulated-preview mode unavailable. Record exact `PREVIEW_SIMULATION_UNAVAILABLE` evidence. Use an already-approved supported alternate validation only when it meets the same canonical evidence requirement; otherwise validation remains unresolved. Mode B is separately checked and can execute real actions, so this simulation gate neither universally blocks Mode B nor blocks unrelated operations. CLI help proves a command surface only, not auth, license, runtime, or action readiness.

## The action log
Under each attempt's checkpoint in the task's change log, also write `- why: <the item's criterion, or the beat it serves>` and `- via: <the qualified skill, Scout helper or command that made the change>`, with the edit tools. The log then shows what was done, with which skill, in which org, why, and the result.

## Lifecycle Center teams
In a team whose `mode` is `lifecycle` (`prompts/scout/team-lifecycle.md`), the `dx-devops` skills run with these lines, measured live against the CLI they drive:
- **`dx-devops-work-item-manage`:**
  - On the Git path, open the review right after the push. Don't wait for the hub to record the commit; the captain's delivery syncs it.
  - Before the first edit, the work item carries the builder's checked base: a line `Checked: <main commit>`, written by `scout_lc.py package start` or `package check`. Rewriting the description with `update --description` keeps that line and the `Components:` line.
  - Its answers: the list is under `.result.workItems[]`. `create` returns a 15-character `workItemId` and `workItemName`, with no branch. `update` returns `status` as `IN_PROGRESS` whatever the new status is, so read the work item back to confirm a transition. `review create` returns `{success, url}`.
- **`dx-devops-project-manage`, `dx-devops-pipeline-manage`:**
  - Name the DevOps Center CLI plugin's first-use install before the first `sf devops` call.
  - Bundle their writes into one yes, and give the SE the link that `stage environment add --no-browser` prints. That command prints it only without `--json`, and waits 5 minutes for the sign-in. For a sandbox, give the link on the org's own My Domain (`https://<MyDomain>--<sandbox>.sandbox.my.salesforce.com` in place of `https://test.salesforce.com`): the generic login reuses whatever sandbox session the browser has. Ask the SE to check the username on the Allow page, and connect environments the day before, since a new environment's sign-in can take minutes to start working.
  - **Switching a member's GitHub account:** they revoke their own access in their personal Settings (not Setup): External Credentials, the `ALMDevOpsGitHub` tile, Revoke Access. Then they connect again in Lifecycle Center. Never delete that Named Credential or its principal in Setup: that breaks Lifecycle Center's GitHub link for the whole org.
- **The `dx-devops-test-*` skills:**
  - Their Prerequisite 1 (`sf org list`) becomes `sf org display --target-org [hub]`.
  - Never assign a provider's Default Suite to a stage: it runs every test in the org, and Scout's delivery stops on it.
  - Provider entries carry `id` and `name`. A suite run answers `testSuiteGroupExecutionId`: poll `DevopsTestSuiteExecution` by `DevopsTestSuiteGroupExecId`, expect one row per suite, and allow about 10 minutes for them to settle.
- **IDs:** `promotion complete` and `promotion validate` take 15-character work-item IDs. An 18-character one crashes `complete`'s validation.
- **Promotion faults, measured:** when a new component's files reach the work item's branch in separate commits (the source file, then its meta file), `promotion complete`'s default mode ("only changes missing") resolves no components ("No components to deploy — the resolved component set was empty"), in Lifecycle Center's UI too, and a retry fails the same way. One commit with both files, or a later commit changing it, deploys. Commit a new component's files together. `--deploy-all` (all metadata in the stage branch) gets past it; Scout's `deliver --full` checks every component on `main` first. A failed promotion records its merge too, so only a successful one marks a delivery.
- **Rules for builders without Scout:** a Scout override can't reach Cursor or Vibes, so the same rules are Scout's block in the team repository's `AGENTS.md`, which `scout_lc.py start` adds next to the team's own text.

## Hosts
Scout drives these plugins on Claude Code only, although Salesforce also ships them for Codex. On Codex, items that need an official skill are BLOCKED by name with "needs Claude Code, or a local sf-skills checkout", unless `SCOUT_OFFICIAL_SKILLS_ROOT` names a local checkout of Salesforce's `sf-skills` repository. Then read the skills in place from `<checkout>/plugins/builder/<plugin>/skills/<skill>/SKILL.md`, never copying them. Scout's own rules, `sf-demo-scout:sf-flow` and the `sf` CLI work on both hosts.
